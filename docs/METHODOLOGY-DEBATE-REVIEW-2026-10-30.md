# Методологічна рецензія: дебати й узгодження — 2026-10-30

## Процедура

Цей документ фіксує застосування трьох зовнішніх skill-підходів у заданій користувачем послідовності. Це не твердження, що GitHub-репозиторії запустили автономних агентів або що їхні автори брали участь у рецензуванні. У цій сесії їхні опубліковані інструкції застосовано як окремі аналітичні процедури.

1. **obra/superpowers — перший етап.** Спочатку встановлюються фактичний стан репозиторію, межі продукту, існуючі артефакти, структура результату та критерії прийняття. Результат: не створювати дубльовану методологію; розкласти її на публічний опис, повну технічну методологію та реєстр доказів.
2. **Imbad0202/academic-research-skills — незалежний академічний перегляд.** Перевіряються дослідницьке питання, методологічна логіка, структура, узгодженість тверджень із результатами, обмеження й відтворюваність.
3. **K-Dense-AI/scientific-agent-skills — незалежний доказовий перегляд.** Перевіряються provenance, джерела, знаменники, статистика, версії даних/моделей, відокремлення фактів від припущень і повнота disclosure.
4. **Дебати й adjudication.** Розбіжності вирішуються за першоджерелами, кодом, workflow logs та benchmark artifacts; голосування або компромісне формулювання не замінюють доказ.

## Питання 1. Чи потрібно представити проєкт як «повністю точний корейсько-український стандарт»?

- **Академічний reviewer:** ні. Наявні діагностичні корпуси й регресії не дорівнюють незалежно adjudicated нормативному holdout.
- **Evidence reviewer:** погоджується; окремо забороняє переносити IPA exact-match у твердження про українську цільову якість.
- **Рішення:** проєкт описується як авторська дослідницька практична система. Її архітектура, детермінованість, джерельні правила й реальні експериментальні результати — сильні досягнення; абсолютна мовна точність не заявляється.

## Питання 2. Як показувати результати native проти g2pK?

- **Академічний reviewer:** потрібно показувати корпуси окремо, пояснювати різні результати й не оголошувати універсального переможця.
- **Evidence reviewer:** вимагає парних знаменників, coverage, abstentions, довірчих інтервалів, точного IPA normalization profile та спільного renderer caveat.
- **Рішення:** UGTPHON демонструє близькі exact-match результати без переконливої різниці в парному порівнянні; SIGMORPHON дає невелику статистично помітну native exact-match перевагу. CER на обох корпусах не встановлює чіткої переваги. Ці результати публікуються як діагностика Korean IPA.

## Питання 3. Чи потрібно показати CharsiuG2P, хоча його результати значно кращі?

- **Академічний reviewer:** так. Виключення сильного baseline створило б упереджений огляд.
- **Evidence reviewer:** так, але обов'язково розділити observed score та незалежну generalization evidence; показати training-overlap і ліцензійні блокери.
- **Рішення:** показувати 88.531% exact на UGTPHON і 70.971% на SIGMORPHON, разом із CER/PER, одноразовим cold timing, 508/729 потенційними перетинами та невідомим повним training manifest. Називати strong research teacher/baseline, не gold oracle і не production dependency.

## Питання 4. Чи можна використати runtime як конкурентну перевагу?

- **Академічний reviewer:** так, якщо це окремо від фонетичної точності.
- **Evidence reviewer:** тільки з однаковим timing scope, повторними вимірюваннями й описом середовища.
- **Рішення:** UGTPHON має п'ять повторів native/g2pK: медіани 366.002 ms і 17,412.489 ms. Це близько 47.6× у межах цього harness. Не узагальнювати на інші пристрої, браузери або режими.

## Питання 5. Що доводить зелений CI?

- **Академічний reviewer:** програмну стабільність і відтворення задекларованих тестових очікувань.
- **Evidence reviewer:** не незалежну фонетичну правильність, не репрезентативність корпусу й не оптимальність українських форм.
- **Рішення:** окремо публікувати CI verification і linguistic validation status. На main commit `f93ae007592f216ccd2493f6652d228b876c8338` підтверджено 1,340/1,340 browser tests, Python 3.11/3.12/3.13, data/system checks, build і Pages deployment. Незалежна IPA та Ukrainian gold лишаються evidence-limited.

## Невирішена технічна суперечність

PR #371 містить актуальні розширені вимірювання, але його гілка `bench/extended-metrics-runtime-2026-10-29` розходиться з main (117 commits ahead, 26 behind) і лишається non-mergeable. У run 40843579685 neural pairing job справді впав через відсутній `per_engine_occurrences` у baseline report. Цей конкретний schema defect усунуто в окремому PR #399: baseline producer тепер формує повний occurrence ledger для кожного рушія, а workflow перевіряє schema v1, кількість, порядок, ідентичність і score fields. На точному head `ad7ce7caf1dc56f22449a88b2c565e049d95873d` run 41123471367 пройшов для обох корпусів; завантажений artifact містить 2,703 UGTPHON і 999 SIGMORPHON входжень для шести рушіїв. Водночас neural inference і joined pairing jobs на цьому PR були SKIPPED через їхню окрему research-only opt-in умову. Отже, producer/schema fix тепер DONE_VERIFIED на PR #399, але свіжий joined neural-vs-baseline result залишається PARTIAL до окремого контрольованого запуску. Це не робить гілку PR #371 автоматично придатною до merge.

## Узгоджена редакційна політика

- Не применшувати виміряні досягнення власного рушія, особливо прозорість, детермінізм, контрольовані відмови й runtime.
- Не приховувати сильні результати зовнішніх моделей.
- Не підміняти мовну валідацію тестами коду.
- Не перетворювати ризик contamination на твердження про доведене leakage.
- Не приписувати моделі ліцензію, якщо вона не підтверджена для саме ваг.
- Кожна цифра в публічному тексті повинна мати run, corpus, denominator, metric, version і interpretation note.
